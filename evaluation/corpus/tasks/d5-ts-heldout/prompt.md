# Relay: translate capture failures into safe agent actions

Handle `{grantId,accountId,toolCallId,operation,orderId}`. `tool_grants[grantId]` supplies accountId, approved, operation:'capture', intentId and orderId; the authorized intents row supplies amountMinor and currency. Validate the exact operation, resource and account on every invocation, including cached outcomes; invalid authority is denied/403, code POLICY_DENIED, retryable:false. A new toolCallId never replaces the durable business capture identity. The endpoint only captures the granted known order.

Persist a claim before capture. A matching COMPLETED capture creates one `entitlements[intentId]` and returns completed/200, code CAPTURE_CONFIRMED, retryable:false, captureId. PENDING returns pending/202, code CAPTURE_PENDING, retryable:false. Missing/malformed responses, connection failure, 408 or 5xx may hide a committed write: reconcile the known order, and if unresolved return unknown/202, code OUTCOME_UNKNOWN, retryable:false while preserving protection.

Distinguish definite errors without a reconciliation read: OAuth/authentication or encoding before dispatch is not_sent/503, code AUTHENTICATION_UNAVAILABLE or INVALID_REQUEST, retryable:true; API 401/403 is refused/422, code PROVIDER_AUTHORIZATION, retryable:false; 429 is rate_limited/429, code RATE_LIMITED, retryable:true; other explicit 4xx refusals are refused/422, retryable:false with typed issue or PROVIDER_REFUSAL fallback. Unknown/default error arms must not crash. Keep unexpected local/programming exceptions visible. Do not turn every operational failure into an agent instruction to retry a new payment.
