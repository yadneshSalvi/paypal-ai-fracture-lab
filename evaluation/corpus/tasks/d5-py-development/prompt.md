# Errand Python: a refund tool must expose the right recovery action

Handle `{permissionId,accountId,toolCallId,operation,captureId,amountMinor}`. `tool_permissions[permissionId]` contains approved, accountId, operation:'refund', refundIntentId, intentId, captureId, amountMinor, currency and maximumMinor. The bound intent must belong to the same account and be authorized. Validate all immutable arguments and the ceiling before any provider traffic, including cached replays. Invalid authority is denied/403, code POLICY_DENIED, retryable:false.

The refundIntentId is the business identity across repeated model tool calls. Persist its immutable operation and explicit provider request ID before dispatch. A matching COMPLETED refund is completed/200 with code REFUND_CONFIRMED, retryable:false and refundId; PENDING is pending/202, code REFUND_PENDING, retryable:false. A known refund ID may be read on replay. Lost or malformed answer without a valid ID is unknown/202, code OUTCOME_UNKNOWN, retryable:false and must never be dispatched again automatically.

Translate errors precisely: OAuth or proven connect-before-send failure is not_sent/503, code AUTHENTICATION_UNAVAILABLE or REQUEST_NOT_SENT, retryable:true. API 401/403 is refused/422, code PROVIDER_AUTHORIZATION, retryable:false. 429 is rate_limited/429, code RATE_LIMITED, retryable:true. Other explicit 4xx refusals preserve a typed issue code or PROVIDER_REFUSAL fallback and are refused/422, retryable:false. 408/5xx and read-side failures leave uncertainty protected. Unknown/default error bodies must degrade safely. Save operation state in `tool_refunds[refundIntentId]`; keep unexpected store/programming exceptions visible.
