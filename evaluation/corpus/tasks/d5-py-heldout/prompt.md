# Atlas: an approved two-step payment plan survives model replanning

Handle `{planId,accountId,toolCallId,step,orderId?}` where step is create or capture. `approved_plans[planId]` has accountId, approved, intentId and maximumMinor; the immutable intent supplies authorized, accountId, amountMinor and currency. Validate plan authority and budget on every call. A bad scope or mismatched order hint is denied/403, code POLICY_DENIED, retryable:false. Calling capture before an order exists is out_of_order/409, code CREATE_REQUIRED, retryable:false with no provider traffic.

The approved plan is stable while a model may issue new toolCallIds. Persist each step's claim before dispatch and use explicit provider identities tied to the approved business operation. The create step returns ready/200 with orderId only after a matching resource is confirmed; subsequent create calls return the same order. An unknown create without a valid ID stays protected and is unknown/202, code OUTCOME_UNKNOWN, retryable:false. Never invent a lookup or restart the plan to make another order.

Capture only the persisted plan order, reconcile that known order after response loss, and require a matching COMPLETED capture before granting one `entitlements[intentId]` row. Record orderId, captureId and state in `plan_receipts[planId]`. Completed capture is completed/200 with code CAPTURE_CONFIRMED, retryable:false; pending is pending/202 with code CAPTURE_PENDING. Unknown results never instruct the agent to replay a new payment. Proven pre-dispatch authentication failures are not_sent/503, code AUTHENTICATION_UNAVAILABLE, retryable:true; explicit provider refusals are refused/422 with retryable:false. Optional missing fields and programming/store exceptions require their distinct handling. The offline workspace models controlled approval between the two steps; it is not an automated real buyer approval.
