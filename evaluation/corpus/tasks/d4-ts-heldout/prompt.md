# Vale: a return case contains distinct immutable refund lines

Handle `{caseId,lineId,accountId,amountMinor,attemptId}`. `return_cases[caseId]` contains accountId, approved, intentId, captureId, and `lines:[{id,amountMinor}]`. Case and line identifiers contain no slash. A case-line pair, represented as `caseId + '/' + lineId`, is the semantic refund identity. Attempts, retries, process restarts, and new tool invocation IDs do not change it. Different approved lines on the same case are separate legitimate partial refunds.

Validate account, case authority and exact line amount before every effect, including cached replays. A changed amount returns conflict/409 without making a provider request. The bound intents row contains original captured amount and currency; verify the capture before dispatch. Reserve capacity locally before sending; unknown, pending and completed operations retain it. There are no external refunds in this task. Do not use the generic Idempotency-Key as the provider refund identity. Persist each operation's immutable body and explicit provider request ID before dispatch, and persist one `return_results[caseId+'/'+lineId]` containing refundId, captureId and amountMinor after a confirmed matching COMPLETED refund.

An unknown answer cannot authorize a second refund. Return completed/200 with refundId, pending/202, unknown/202, capacity/409, conflict/409, forbidden/403, refused/422, or not_sent/503 as appropriate. A valid persisted refund ID may be reread. Never suppress programming/store failures, mutate the original authorization, or merge separate return lines.
