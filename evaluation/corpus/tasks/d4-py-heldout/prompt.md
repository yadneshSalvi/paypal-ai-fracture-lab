# Lantern: restartable refund batches have per-item identities

Handle `{batchId,accountId,deliveryId}`. `refund_batches[batchId]` is immutable approved authority with accountId and items, each containing refundIntentId, intentId, captureId, amountMinor and currency. Validate batch and all bound intent account scopes before dispatching any item. Intents store each original captured amount. A batch can contain multiple legitimate refund intents for the same capture. A delivery ID or batch ID alone is therefore not the identity of a refund operation.

Each refundIntentId needs a durable immutable operation and an explicit provider request ID. Atomically reserve local captured capacity per item; no external refunds exist here. Concurrent delivery or restart of a partially completed batch must not redispatch any completed, pending or unknown item. A known refund ID may be reread; an unknown item without one remains protected. Other authorized items may continue. Insert one `batch_refunds[refundIntentId]` with batchId, refundId and amountMinor only after a matching COMPLETED refund. Pending/unknown reservations stay held. Explicit refusal or proven pre-dispatch failure may release their capacity.

Return `{status,httpStatus,items:[{refundIntentId,status,refundId?}]}`. Overall completed/200 requires all items completed. Otherwise use unknown/202 if any unknown, pending/202 if all are completed/pending, or the applicable capacity/409, refused/422 or not_sent/503 state. Foreign account returns forbidden/403 before any effect. Unexpected local errors must escape. Do not change approved items or collapse multiple same-capture lines into one refund.
