# Harbor access projection: stale notifications cannot reopen refunded access

Handle `{accountId,event}`. Verify the exact event before reading or mutating target state. A normalized signed envelope contains id, event_type and resource.capture_id. `capture_bindings[capture_id]` maps to intentId; the authorized `intents` row supplies account scope and captured amount/currency. Events can describe capture completion, partial refund or full refund, and may be repeated or delivered in reverse order. Use the SDK's authoritative capture GET to establish the current state instead of ranking event timestamps.

Maintain `payment_state[intentId]` containing captureId, amountMinor and state `paid`, `partially_refunded`, or `refunded`. This progression is monotonic; a stale observation must never move it backward. `access[intentId]` contains active:true for paid or partially_refunded and active:false for refunded. Full refund also creates one `refund_notices[intentId]` record. Repeated and concurrent notifications must remain safe and resumable across store failures. Only a bound matching capture may affect the projection; unknown/malformed fields or unavailable reads return unknown/503 without fabricating a state. Invalid signature is invalid/401; account or provider binding mismatch forbidden/403; accepted projection updates return accepted/200. No provider writes are allowed, and unexpected local failures must propagate.
